  Two stacked bugs, both systemic (not prefixsearch-specific):

  1. ApiQueryPrefixSearch::getAllowedParams() (and ApiQuerySearch's, and
     ApiOpenSearch's - all 3 `use SearchApi;`) just calls
     `$this->buildCommonApiParams()`, a shared trait method, not a static
     PHP array literal - extract_mediawiki_api.py's parser can only read
     literal `return [...]` arrays, so this extracted to nothing. This
     wasn't unique to the autocomplete box: `list=search`'s own `srsearch`
     (the actual search query text!) was equally missing the whole time.
     Fixed: extract_mediawiki_api.py now detects `use SearchApi` and merges
     in the trait's known field set (search/namespace/limit/offset) with
     the module's own wire prefix.

  2. `generator=X` is a completely generic MediaWiki API mechanism - any of
     the ~24 core list=/prop= submodules that extend ApiQueryGeneratorBase
     can be used as a generator, and doing so prepends an extra "g" to
     every one of that submodule's own param names (list=prefixsearch's
     `pssearch` becomes generator=prefixsearch's `gpssearch`). Nothing in
     the WAF had ever modeled this g-prefix mechanism at all, for any of
     the 24 modules, not just prefixsearch. Fixed: resolve_query_submodule_
     fields() (in mediawiki.lua, generated by integrate_api_tiers.py) now
     adds a g-prefixed copy of every prop/list submodule's fields when
     `v.generator` names it, AND the static mw_query_submodule_fields_union
     (the base api_schema object - checked BEFORE api_check's per-request
     logic ever runs, so it has to allow these names too or nothing past it
     matters) gets the same g-prefixed widening.
